# 接入独立向量库 Milvus（检索层存储后端：PGVectorStore → 原生 pymilvus）

> **状态：已定稿、待实施（2026-10-12）**。本文档为实施规格（spec: `milvus-vector-store`），由 Trae 按此执行；实施前先冻结 `rag_index/retriever/kb_api/tests` 相关文件，避免双工具并发编辑冲突。

## Context（背景与动机）

**现状**：检索层已按《RAG检索层改造方案_LlamaIndex_2026-10-12》全量落地——主通道 `backend/app/services/rag_index.py`（LlamaIndex VectorStoreIndex + PGVectorStore 自管主库 `data_kb_dense` 表）、智谱 embedding-3 2048 维（`backend/app/llm/embed_client.py`）、`backend/app/services/retriever.py` 三分支降级链、`kb_api.py` 五处状态同步（`sync_entry`）、`init_db.py`/`reindex_rag.py` 脚本、gated 测试夹具均已就位。

**要解决的问题**：
1. pgvector 是主库扩展模式（向量数据与业务库同实例），与架构 T-2 决策项「独立向量库 vs 主库扩展」的**独立库**方向不符；
2. 2048 维超出 pgvector ivfflat/hnsw 的 2000 维上限 → 无法建 ANN 索引，只能顺序扫描；
3. 向量层部署/扩容/备份与主库耦合。

**目标**：向量存储后端替换为独立部署的 Milvus（3.0.2 standalone）——2048 维可建 HNSW、集合级 Strong 一致性、原生 upsert；`rag_index.py` 对外接口（`available/query/upsert_entry/delete_entry/sync_entry/reindex_all`）签名与返回契约完全不变 → `retriever.py`/`kb_api.py` 业务接线零改动。LangGraph 编排、嵌入通道、降级链（spec D6）全部不动。

**路线决定**（用户确认「使用最佳方案」，即）：**原生 pymilvus 3.x + Milvus 3.0.2**。否决 LlamaIndex 封装路线的原因：`llama-index-vector-stores-milvus` 1.2.0 锁定 `pymilvus[milvus-lite]<3`，无法搭配 Milvus 3.0.2 服务端（被迫降级部署 Milvus 2.6.x），且其查询一致性为默认 Session 级、无逐调用覆盖，不满足「下架内容绝不泄露」所需的 Strong 语义。llama-index 依赖在检索层随之退出（embedding 通道是自定义 httpx 实现，本就独立于 LlamaIndex）。

## 已核实的关键技术事实（可直接依赖）

- Milvus 3.0.2 standalone 官方部署＝三容器（milvus + etcd v3.5.25 + minio）；SDK 端口 19530、健康/指标端口 9091（健康检查 `GET /healthz`）
- pymilvus 3.x `MilvusClient`：自定义 schema `create_collection(schema=…, index_params=…, consistency_level="Strong")`；HNSW 参数合法域 M∈[4,64]、efConstruction∈[8,512]；metric `COSINE`；`float_vector` 维度上限 32768（2048 维可正常建 HNSW）；**原生 upsert**（无需 delete+add）；`delete(ids=[…])` 按主键删；`search(filter="表达式")`，表达式支持 `== / in / and / or / not`；默认一致性 Bounded（写入后读可能滞后）→ 集合级 `Strong` 显式覆盖
- COSINE 下 search 返回的 `distance` 即余弦相似度（越大越相似），与现有打分口径一致
- 不可变契约（三路径一致）：候选 top8 → 0.6×余弦 + 0.4×关键词 → 前 5；输出 `{kb_id, kb_version, title, content, preconditions, stance, topic_key, domain}`
- 哨兵语义：`age_band`/`species` 空值存 `'any'`（过滤 `in [value, 'any']`），与 Python 降级分支完全同构
- 可复用现状：`embed_client.embed_texts`（智谱 2048 维，批次 ≤64，mock 兜底）、`sync_entry` 状态分派逻辑、`reindex_all` 批处理骨架、conftest 环境强制模式（REDIS_URL/CRYPTO_PROVIDER/EMBEDDING_PROVIDER 同款写法）

## 设计

### 集合 schema：`jiaban_kb_entries`（单集合）

| 字段 | 类型 | 说明 |
|---|---|---|
| kb_id | VarChar(64)，主键 | 知识条目业务编号（= KbEntry.kb_id） |
| embedding | FloatVector(2048) | 维度 = `settings.embedding_dimensions` |
| status | VarChar(16) | 过滤键（published 等） |
| kb_kind | VarChar(8) | 过滤键（child / pet） |
| domain | VarChar(32) | 过滤键（英文码或中文别名） |
| age_band | VarChar(16) | 空值写哨兵 `'any'` |
| species | VarChar(16) | 空值写 `'any'`，仅 pet 域参与过滤 |

- 索引：HNSW（M=16，efConstruction=200），metric COSINE，搜索时 `ef=128`；一致性 **Strong**
- 只存向量 + 过滤标量 + 主键；正文不落 Milvus，检索命中后按 kb_id 回主库取条目
- 向量输入 `f"{title}\n{content}"`（与降级链 hashing 口径同源），经 `embed_texts` 生成

### 一致性双保险（「下架内容绝不泄露」不变式）

1. 集合级 Strong：`sync_entry` 的 delete/upsert 调用返回后查询侧立即可见；
2. 检索侧复核（防御纵深）：`retriever._retrieve_by_index` 的候选回查追加 `KbEntry.status == "published"` 且 `KbEntry.kb_kind.in_(("child","pet"))` 条件——并入现有单次 `.filter(KbEntry.kb_id.in_(…))` 调用（多条件即 AND），既有测试 mock 链（`.filter.return_value.all`）无需改动。

### 过滤表达式（`build_filter_expr` 替代 `build_filters`）

```python
# rag_index.build_filter_expr(domain_alias, age_band, species) -> str
#   status == "published" and kb_kind in ["child", "pet"] and domain in [...]
#   [+ and age_band in ["<v>", "any"]]   # age_band 非空时
#   [+ and species in ["<v>", "any"]]    # 仅当 "pet" ∈ domain_alias 且 species 非空
```
- **注入防护**：所有插入表达式的值先过白名单正则（如 `^[\w\u4e00-\u9fff.\-]+$`），不合法值丢弃该条件（绝不原样拼接）
- 哨兵与别名语义与旧 `build_filters` 完全同构（domain 英文码/中文别名双包含）

### 客户端与探测

- `get_client()`：进程内单例，`MilvusClient(uri=settings.milvus_uri, token=settings.milvus_token or None)`
- `available()`：`milvus_uri` 空 → False（快路径，不发起连接）；否则 `has_collection` 探测——成功缓存 True、失败不缓存（Milvus 后启即可自动恢复）
- `ensure_collection()`：集合不存在则建（schema + 索引 + Strong + `load_collection()`），供 `init_db` / `reindex_all` 调用；运行期不自愈建表（异常回退降级链）
- `query()`：`client.search(collection_name, data=[vec], filter=expr, limit=top_k, search_params={"metric_type":"COSINE","params":{"ef":128}})` → `[(hit["id"], hit["distance"])]`（主键即 kb_id），按相似度降序

### 配置（`backend/app/core/config.py` 新增「向量库」节）

- `milvus_uri: str = ""`（空＝主通道禁用 → 降级链；compose 注入 `http://milvus:19530`，本地开发 `backend/.env` 用 `http://localhost:19530`）
- `milvus_token: str = ""`（可选；standalone 默认无鉴权）
- 集合名用模块常量 `COLLECTION_NAME = "jiaban_kb_entries"`（不引入配置项）

### 降级链（保持不变，spec D6）

| 情形 | 行为 |
|---|---|
| `MILVUS_URI` 空 / pymilvus 缺失 / 探测失败 | `available()=False` → hashing JSONB + Python 余弦 → 纯关键词 |
| 查询时异常（Milvus 不可达等） | `_retrieve_by_index` 捕获 → 本次回退降级路径 + warning |
| 写入同步失败 | `sync_entry` 吞异常 + warning（best-effort）；Strong + 检索侧复核兜底，`reindex_all` 自愈 |
| `EMBEDDING_PROVIDER=mock` / key 空 | 全链路 mock 嵌入，确定性（conftest 强制） |

### 保留物（回滚保险，不删）

`data_kb_dense` 表、`kb_entry.embedding_vec` 列、`migrate_pgvector.sql`、`run_pgvector_migration.py`（deprecated 头注）全部保留、代码停用。回滚 = 恢复 llama-index 依赖 + 旧版 `rag_index.py`。

## 风险与注意

- **表达式注入**：过滤值一律白名单校验后插入（Milvus expr 与 SQL 同级注入面）
- **一致性**：Strong + 检索侧复核双保险；代价为查询略慢（数据量小可忽略）
- **幂等**：原生 upsert；`reindex_all` 为 drop+重建（维护动作，执行窗口自控；期间检索走降级链）
- **依赖变更**：llama-index 卸载前确认零引用（`rag_index.py` 为唯一触点）；镜像体积随之下降
- **资源**：Milvus 三件套内存占用写入部署文档
- **并发编辑**：实施前冻结 `rag_index/retriever/kb_api/tests` 相关文件，避免双工具互相覆盖
- **维度变更路径**：schema 维度 = `embedding_dimensions`，变更需 drop + reindex（`reindex_rag.py` 已覆盖）
