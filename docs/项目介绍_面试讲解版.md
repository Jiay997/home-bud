# Babe宝伴｜AI 多智能体家庭养育科普参考工具 — 项目介绍

> 用途：面试现场陈述与追问应答。全文按「定位 → 用户 → 问题 → 解法 → 技术 → 成果 → 我的贡献 → 话术」八层递进。
> 数据口径：均取自本仓库实际代码与文档（`backend/`、`client/`、`admin-web/`、`docs/`），截至 2026-10-20。

---

## 一、一句话定位

**Babe宝伴是一个面向「家庭养育」垂直领域的 AI 多智能体助手：只做两件事——0–6 岁分龄育儿，猫狗科学饲养；并把「孩子和宠物一起生活」这类单一工具答不全的复合问题一次答清，且在高危场景下宁可一个字都不生成。**

三个关键词概括它与通用 AI 助手的区别：**垂直**（只做两个板块，不做通用问答）、**交叉**（育儿 × 宠物的复合场景）、**安全前置**（风险拦截发生在模型生成之前，而不是事后审核）。

形态上是一套源码双端交付：微信小程序（C 端首发唯一端）+ H5（同一份 uni-app 源码编译）+ 后台管理 Web。

## 二、目标用户：谁在用、在什么场景用

### 2.1 主用户画像（五类，按「孩子月龄 × 是否养宠」切分）

| 画像 | 特征 | 核心诉求 | 付费意愿 |
|---|---|---|---|
| P-婴儿 | 孩子 0–1 岁，首次养育，焦虑度高、提问频次高 | 快速判断「该听谁的」，要依据不要结论 | 中 |
| P-幼儿 | 孩子 1–3 岁，睡眠、喂养、行为引导问题集中 | 分龄贴合、可执行、能对照观察 | 中高 |
| P-学前 | 孩子 3–6 岁，社交、情绪、入园适应 | 场景化沟通方法，边界清晰 | 中 |
| P-宠物 | 家有猫或狗，部分同时有孩子 | 行为解读、喂养、急症识别 | 中 |
| **P-交叉** | **同时有 0–6 岁孩子与猫狗（核心人群）** | **一次问、三面答，安全优先** | **高** |

### 2.2 使用现场（这一条决定了全部设计决策）

不是坐在电脑前从容提问，而是：**单手操作**（一手抱孩子）、**碎片时间**（喂奶间隙、孩子睡着后）、**夜间低光**（夜醒是最高频的提问场景）、**情绪可能处于焦虑甚至崩溃状态**。

这三个物理约束直接推出了三个产品决策：主操作区必须落在屏幕下半屏可达区；深色模式是一等公民而非附加项；必须有「高危输入拦截」这条独立链路——因为真实用户会在情绪崩溃时向它求助，而这类输入绝不能被模型自由发挥。

**明确不服务的对象**：6 岁以上儿童家庭、学科辅导需求、机构客户（早教机构、宠物医院）、需要诊疗结论的用户。

## 三、核心问题与痛点

产品立项时做了 6 条痛点归因，每条都对应一个明确的产品动作，不是「体验优化」而是「缺一块就失效」：

| 编号 | 痛点 | 现状替代方案 | 为什么不够用 | 产品动作 |
|---|---|---|---|---|
| PB-1 | 信息嘈杂且互相矛盾 | 短视频、母婴社群、长辈经验三套说法并行 | 同一问题三种答案，**都不给适用前提**，用户无法判断哪条适用于自家孩子 | 结构化输出：建议要点 + **适用前提** + **不建议做法的原因** |
| PB-2 | 气质话题热度高但缺科学配套 | 市面内容偏玄学，只给标签不给方法 | 给了「类型」但不给可执行的养育方式，也无法说明「这不是宿命」 | 测评 + 配套养育方式，**输出三档区间而非唯一类型** |
| PB-3 | 育儿与养宠的交叉问题无工具承接 | 育儿工具只答孩子，宠物工具只答宠物 | 「孩子追猫、猫哈气」被拆成两半回答，**没人负责两者的安全交集** | **一次问、三面答**：安全提示置顶 + 育儿侧 + 宠物侧 |
| PB-4 | 通用大模型给结论不给边界 | 直接问通用对话模型 | 回答流畅但无档位、无禁忌项、无来源；**遇到自伤、虐待、惊厥类输入仍照常生成内容** | 风险扫描前置到生成之前，命中即**不生成任何内容** |
| PB-5 | 宠物 AI 问诊直接给诊断与用药 | 部分产品宣称「精准诊断并输出用药建议」 | 与「不诊断、不开方、不给剂量」的合规红线正面冲突 | 药名 + 剂量模式一律拦截或改写；只做行为科普 |
| PB-6 | 儿童个人信息处理门槛高 | 小团队往往直接跳过或粗糙处理 | 儿童信息属敏感个人信息，需监护人单独同意、可撤回、可删除 | 分层同意 + 字段加密 + 权利中心 + 删除回执，全链路留痕 |

**共性根因**：这六个问题不是「AI 不够聪明」，而是**缺少一个愿意为边界负责的产品结构**。所以整个项目的设计重心不在提示词调优，而在「谁能决定不回答、不回答时给什么、回答了怎么追溯」。

## 四、产品解法：四个立得住的支点

### 支点一：安全先于完整——风险拦截前置于生成

执行顺序是硬约束：**收请求 → 鉴权与幂等 → 风险扫描（纯输入侧，不读用户档案）→ 意图识别 → 检索 → 领域 Agent 并行 → 汇总 → 输出侧过滤 → 返回**。

风险扫描走两级流水线：一级是词库 + 正则（含药名剂量模式、急症表述、语境排除规则），命中直接阻断，不调模型；一级未命中才进二级语义分类，按分数分档：**>0.8 拦截 / 0.5–0.8 拦截并给温和引导 / <0.5 放行打标**。两条保守规则贯穿全局：**硬类别（虐待、自伤、急症、动物咬伤）永不自动放行**；**语义模型超时或不可用一律按命中处理**，不做「降级放行」。

命中后的行为是产品级的：**正文为空**，只给危机引导与线下机构入口。这条「命中后不输出任何内容 = 100%」是唯一保留 100% 口径的指标——因为「拦截率 100%」本身不可达（会漏报），所以目标被拆成「召回 ≥95% + 误报 ≤5% + 命中后零正文」三件套。

同步还有输出侧过滤：生成完成后每个内容块再过一遍词库与正则，命中即置空。**入口和出口都设关**，而不是只赌入口。

### 支点二：一次问、三面答——多 Agent 并行 + 服务端定序

复合问题（「孩子追猫、猫哈气」）会并行调用三个领域 Agent：育儿、宠物、家庭安全。关键设计有两条：

1. **渲染顺序由服务端决定，前端不得重排**。`render_order` 固定为 `["safety", "child", "pet"]`，安全分节 `pinned: true`，不可折叠、不可下移。
2. **汇总不等于再调一次模型**。聚合节点用「模板骨架 + 字段填充」实现，**不调用 LLM**；不可改写字段（安全提示、冲突标注、免责声明、AI 生成标识、转介提示）由服务端注入，模型无权改动。这样既省一次调用成本，也消除了「模型把免责声明改写掉」的风险。

### 支点三：给区间，不给定论

所有判定以档位 / 区间 / 置信度呈现，由结构化输出契约（JSON Schema 级约束）强制，不只靠提示词：测评维度分三档而非唯一类型；检索无命中时强制标注 `professional_referral=true`；气质测评明确声明非宿命判定。这条原则的作用是**消除虚假精确感**——尤其在育儿这个「没有标准答案」的领域，给出唯一结论比给出区间更危险。

### 支点四：付费墙在服务端，不在前端

会员内容由服务端裁剪：无权限的内容块**根本不下发 `content` 字段**（不是空串、不是占位符、不是前端遮罩）。前端只负责体验收敛，**不承担任何安全边界**。同理，额度裁决也只在服务端——前端展示的剩余次数只是显示值。

## 五、技术栈与各技术的用途

|---|---|---|---|
| **C 端** | uni-app 3 + Vue 3.4 + TypeScript + Vite 5 | 一套源码同时编译微信小程序与 H5（H5 产物部署在 `/app/`） | 小程序是首发唯一端，但需要 H5 做验收与演示；双端分别维护的成本无法接受 |

| **服务端** | Python 3.12 + FastAPI + uvicorn | 113 个 HTTP 接口、SSE 分块流式、鉴权、限流、幂等、统一响应包络 | `StreamingResponse` 天然承载分块推流；Pydantic 做请求/响应契约校验 |
| **ORM / 模型** | SQLAlchemy 2.0 | 38 张业务表，含加密字段、派生列、乐观锁、幂等表 | 需要精确控制 SQL 与事务边界（额度原子自增、乐观锁冲突） |

| **大模型** | DeepSeek（OpenAI 兼容协议）+ 模型白名单 | 三个领域 Agent 的推理、意图分类、二级风险语义分类 | 仅用境内已备案模型；OpenAI 兼容协议让 provider 可替换（白名单启动时校验，未登记直接拒绝启动） |
| **向量检索** | Milvus standalone 3.0.2 + 智谱 embedding-3（2048 维 / HNSW / COSINE） | 育儿与宠物知识库的语义召回：候选 top-8 → 混合打分精选 top-5 | 知识库需要独立演进与版本绑定；集合级 Strong 一致性 + 原生 upsert，条目下架即时生效 |
| **检索降级** | 字符 3-gram hashing 512 维稀疏向量 + Python 余弦 | Milvus 不可用时的进程内降级链，混合口径不变（0.6×余弦 + 0.4×关键词） | 检索层故障**不能等于服务不可用**；零外部依赖的降级路径保证问答链路仍可跑通 |
| **主库** | PostgreSQL 16（pgvector 镜像） | 业务表 + 幂等表 + 审计 + 高风险事件 + 向量扩展（历史回滚保留） | 强事务、JSONB 承载结构化契约、pgvector 作为向量方案的历史退路 |
| **缓存** | Redis 7（AOF 持久化） | 词库快照缓存、限流、额度计数；未配置时自动回退进程内缓存 | 计数类键重启不能丢；但缓存是可选依赖，缺省必须能跑 |
| **安全** | python-jose（JWT）+ passlib/bcrypt + cryptography（Fernet） | 双端鉴权（C 端微信会话、后台账号 + MFA）、儿童敏感字段加密、密钥多版本轮换 | 儿童出生日期、昵称、过敏项、问答原文属敏感个人信息，必须加密落库且支持轮换 |
| **媒体** | Pillow | 头像与相册的服务端规范化（尺寸、格式、EXIF） | 上传内容不可信，规范化必须发生在服务端 |
| **定时任务** | APScheduler | 对账、留存期清理、孤立会话扫描、告警巡检 | 与 Web 进程同镜像部署，避免为几个定时任务单独引入调度中间件 |
| **测试** | pytest + pytest-asyncio + httpx；前端 `node:test` | 24 个后端测试模块 / 313 个用例；18 个前端测试模块；含并发、幂等、降级、缺陷回归专项 | 安全链路与额度计次这类逻辑必须有可重复的自动化验证，不能靠手点 |
| **部署** | Docker Compose（frontend/backend/postgres/redis/etcd/minio/milvus）+ Nginx + uvicorn | 一键起全栈；Nginx 对 SSE 路径单独关闭 `proxy_buffering` 与压缩 | 流式响应的头号杀手就是反向代理缓冲，必须在部署层显式关掉 |

### 5.2 三个值得在面试里展开的技术决策

**① 小程序没有 `EventSource`，流式怎么落地？**

这是全项目最容易被追问的技术点。小程序 `wx.request` 不支持 SSE 语义，因此统一收敛到一个 `chatStreamClient`：用 `wx.request({ enableChunked: true })` + `onChunkReceived` 逐块收 `ArrayBuffer`，**帧格式仍沿用 SSE 文本帧**（`event:` / `data:`，按 `\n\n` 切帧）。这样做的好处是 Web 端将来可以复用同一套帧协议。

配套解决了四个真实问题：
- **丢帧**：`sequence` 出现跳号时，用该节最近的 `section_done` 覆盖渲染，因此 `section_done` 是强制帧、不能只发 delta；
- **阻断覆盖**：收到 `blocked` 或安全分节降级时执行 `clearAll()`，把已渲染正文清空——**不允许「灰掉但仍可读」**，因为那等于没拦住；
- **断线续传**：`GET .../stream?from_sequence=N` 从 N+1 续发，超过 5 分钟未重连标记为 `orphaned` 但仍落库；
- **降级兜底**：基础库过低或分块不可用时轮询会话详情，结果必须与流式最终态一致。

**② 检索层故障不能等于服务不可用——三分支降级链**

主通道是 Milvus 向量检索；检索抛错或库不可达时，本次请求回退到进程内路径：全量捞取 + Python 侧用 hashing 稀疏向量算余弦 + 关键词命中归一化，**混合打分公式完全不变**（0.6 余弦 + 0.4 关键词），所以降级后排序口径与主通道一致，不会出现「降级后答案风格突变」。

同时修过一个真实的召回缺陷：原实现只过滤 `score == 0`，导致任何存在零星 3-gram 重叠的条目都被当作命中（「误食布洛芬」能召回「幼儿睡眠引导」），进而使 `kb_hit` 恒为 true、「建议咨询专业人士」的提示永不触发。修法是引入**相关性下限 0.10**（实测正常命中 0.12–0.35、噪声 0–0.03），并做成可配置项，生产换真实 embedding 后无需改代码即可调参。

**③ 额度计次的「不计次」规则比计次更难**

免费额度按 Asia/Shanghai 自然日切分（用固定 +8 偏移而非 tzdata，规避 Windows 时区依赖）。规则是：正常生成计次；**失败、被拦截、缓存命中、断线重连重试都不计次**；会员不计次。并发下用 `UPDATE ... SET used_count = used_count + 1` 原子自增，并显式关闭 ORM 的 session 同步，否则 Python 侧再加 1 会造成二次自增。

这类「什么时候不该扣」的规则，恰恰是用户投诉的高发点——拦截了还扣次数，等于惩罚用户求助。

工程上做了几件「超出课堂项目」的事：

- **文档一致性检查器**：改版本号、改名、改状态口径后跑一次脚本，自动检查 7 类问题（引用可解析、旧版不被当现行、口径回归守卫、章号序列、台账一致）。V1.5 收口时人工核对漏了 22 处不同步，就是这个脚本查出来的；
- **缺陷闭环**：每轮验收后登记缺陷编号（如 RB-01 畸形 multipart 被 422 包装成 500、RB-06 儿童同意撤回后健康档案未停展），并补回归用例，而不是修完就算。

## 七、我的贡献

若面试岗位偏产品，重点讲第一、二段；偏研发，重点讲第三、四段。

**① 产品定义：把模糊需求变成可开发、可验收的规格**
- 从一份 1,099 行的原始需求说明出发，产出 5,000+ 行的 PRD 作为唯一基线，并做了 5 轮版本演进（V1.0 → V3.0），每轮都留下变更映射表与效力声明；
- 定义了 6 条痛点、5 类用户画像、7 张场景卡、75 条功能需求、40 项验收清单、9 类状态机的口径；
- **主动做减法**：把 6 岁以上、学科辅导、心理治疗、宠物诊断、直播社区等 12 项明确列为非目标——范围收敛是这份 PRD 最有价值的部分，因为「不做」比「做」更难写。

**② 竞品与差异化：把「多 Agent」从卖点上摘下来**
- 用 GitHub API 直连抓取育儿 / 宠物方向的开源项目（未使用任何搜索引擎摘要），得出三条结论：该方向开源生态极不成熟（育儿最高 43★，宠物 AI 的 star 中位数 0–2）；**「多 Agent 协同」不构成壁垒**（LangGraph / CrewAI / Agents SDK 全为 MIT，任何团队一周可得）；真正能立住的是**育儿 × 宠物交叉场景**与**中文家庭场景的危机分级 / 干预话术 / 转介链路**；
- 结论直接改写了对外口径：禁止把「多 Agent」当差异化，改讲「交叉场景 + 安全前置 + 可追溯」；同时梳理了开源许可风险（最像的几个项目全部无 LICENSE，只能学思路不能抄数据；有现成中文植物库是 CC BY-NC-SA，禁商用）。

**③ 架构设计：把「安全」写进执行顺序，而不是写在文档里**
- 定义分层架构（渠道层 / 接入层 / 编排层 / 领域 Agent 层 / 风险控制服务 / 知识与数据层 / 模型层）与硬性执行顺序；
- 定下 14 条不可协商的架构决策：风险扫描纯输入侧不读档案、安全 Agent 失败宁可不出正文、灰区语义模型不可用按命中处理、汇总不调 LLM、不可改写字段服务端注入、门控裁剪在服务端、缓存命中仍需逐次过风险与门控；
- 延迟预算落到组件级（8 个阶段各自的 P95 与超时行为），并明确「安全链路超时禁出正文」而非降级放行。

## 八、面试陈述稿

### 8.1 60 秒版（开场自我介绍里用）

> 我做过一个叫 Babe宝伴的项目，是一个面向 0–6 岁孩子家庭的 AI 多智能体助手，解决的是「养娃和养宠两件事交叉时没人答得全」的问题。
>
> 它有三个特点。第一是垂直，只做育儿和宠物两个板块，不做通用助手。第二是交叉，用户问「孩子追猫、猫哈气怎么办」，我们一次并行调用育儿、宠物、家庭安全三个 Agent，输出固定是安全提示置顶、育儿侧、宠物侧。第三是安全前置——风险扫描放在模型生成之前，而且是纯输入侧，不读用户档案，一旦命中就不生成任何内容，只给线下机构引导。这一条是整个项目的价值主张：在育儿这种领域，敢说「我不回答」比答得好更重要。
>
> 技术上是一套 uni-app 源码出小程序和 H5，后端 FastAPI + LangGraph 编排，知识库检索用 Milvus 向量库并带三级降级，113 个接口、38 张表、300 多个自动化用例。我负责从 PRD 到架构到落地和测试的全链路。

### 8.2 3 分钟版（被要求「详细讲讲」时用）

按「问题 → 解法 → 技术 → 难点 → 结果」五段推进：

1. **问题**（40 秒）：6 条痛点里最硬的两条是 PB-3 和 PB-4。PB-3 是育儿工具和宠物工具各自只答一半，「孩子和猫的安全交集」没人负责；PB-4 是通用大模型回答流畅但不识别高危信号，家长情绪崩溃时提交自伤或惊厥描述，它照样生成内容。
2. **解法**（50 秒）：对应两个设计。一是三 Agent 并行 + 服务端定序，安全分节永远置顶且不可折叠；二是两级风险流水线，一级词库正则、二级语义分类，硬类别永不自动放行，语义模型不可用按命中处理——我们不接受「降级放行」这种选择。
3. **技术**（50 秒）：小程序没有 EventSource，所以用 `wx.request` 的 `enableChunked` 收分块，帧格式沿用 SSE；丢帧用 `section_done` 覆盖、断线用 `from_sequence` 续传、收到 `blocked` 必须清空已渲染正文。编排用 LangGraph 的 StateGraph，显式画出条件边和并行扇出扇入，而不是黑盒链。
4. **难点**（30 秒）：最难的其实不是 AI，是「不计次的规则」和「降级不能等于放行」。前者决定用户会不会因为被拦截还被扣次数而流失，后者决定安全链路故障时产品是安全还是裸奔。
5. **结果**（20 秒）：113 个接口、38 张表、313 个后端用例，契约零漂移，小程序核心链路已端到端跑通。

## 九、高频追问与应答要点

**Q1：多 Agent 是不是为了技术而技术？单模型一次调用不行吗？**
A：先承认边界——「多 Agent 协同」本身不是壁垒，开源框架一周可得，所以它从来不是对外卖点。用它的真实理由是**可校验**：复合问题需要三份不同领域的证据，单模型会把它们混成一段无法分节、无法定序、无法单独降级的文本。而「安全提示必须置顶且不可折叠」这个要求，只有把安全做成独立节点、由服务端控制渲染顺序才能保证。

**Q2：风险拦截怎么保证不误伤？**
A：三层。一级词库正则带语境排除规则（急症规则命中宠物语境时跳过，避免把宠物急症判成儿童急症）；二级按分数分档，0.5–0.8 是「拦截 + 温和引导」而不是冷处理；被拦截的软类别有申诉通道，24 小时内人工复核，硬类别不自动放行但可登记复核。指标上不承诺「拦截率 100%」——那不可达，改承诺「召回 ≥95% + 误报 ≤5% + 命中后零正文 100%」。

**Q3：为什么自己写向量检索降级，不直接依赖 Milvus？**
A：因为检索层故障不应该等于服务不可用。降级路径用字符 3-gram hashing 到 512 维 + Python 余弦，零外部依赖、跨进程可复现（用 MD5 折叠而非内建 hash，避开 PYTHONHASHSEED 随机化），并且混合打分公式与主通道完全一致，降级后排序口径不变。代价是召回质量下降，所以它只是降级，不是替代。

**Q4：儿童数据合规你具体做了什么？**
A：分层同意（基础同意与儿童信息单独同意必须分离，两个 checkbox 不能合并）、敏感字段加密落库（出生日期/昵称/过敏项/问答原文）、密钥多版本轮换、解密写审计、六类个人信息权利请求、导出链接 24 小时一次有效、删除产出「已删除清单」回执（含未删除项与法定原因）、备份不参与删除但自然过期。合规不是一段文案，是这些字段和状态机。

**Q5：这个项目最大的遗憾是什么？**
A：真实模型没跑满。当前 `LLM_MOCK=true`、`EMBEDDING_PROVIDER=mock`，问答内容由模板组装，向量召回是确定性 mock——所以「检索相关性」「真实模型的 Markdown 排版遵守率」都还没被真实验证。如果重来一次，我会把「先用真实模型跑 200 条标注集」排在写第二个 Agent 之前。

**Q6：如果要支撑 10 倍用户量，你先改哪里？**
A：先测再改。压测建模按 DAU 5,000 / 峰值 300 QPS 预留，第一个瓶颈大概率在同步阻塞的 Agent 推理（当前图是同步 `invoke`），改法是 Agent 节点异步化 + 连接池隔离；第二个是额度与限流的单点（现在是 DB 原子自增 + 可选 Redis），高并发下应把额度前置到 Redis 并做 DB 最终一致对账。

## 十、使用建议

- **按岗位裁剪**：产品岗删掉第五、六章的技术细节，保留「痛点 → 解法 → 竞品结论 → 我的判断」；研发岗保留技术栈与三个技术决策，把第七章换成具体模块与代码位置。
- **只记三个数字**：113 个接口、38 张表、313 个用例。面试官对数字的信任度远高于形容词。
- **准备一个失败案例**：第九节 Q5（真实模型未验证）是现成的诚实案例，比「一切顺利」更可信。
- **不要说的四句话**：「用了多 Agent 所以很先进」（已被自己的竞品分析否定）、「拦截率 100%」（口径不成立）、「支持千万级并发」（无压测证据）、「业内首创」（无检索证据）。
