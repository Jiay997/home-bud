# 「小光景」宠物侧开源竞品调研

> **调研对象**：面向宠物主 / 宠物医院 / 宠物门店的宠物健康与行为 AI 助手
> **数据截止**：2026-10-08（北京时间）
> **Star / 许可 / 更新时间来源**：GitHub REST API（`/search/repositories`、`/repos`、`raw.githubusercontent.com`）实测拉取，非记忆值
> **检索方式**：GitHub 代码仓库搜索 API 多轮关键词 + 仓库页 / README / 数据文件实际抓取

## 0. 先说结论（TL;DR）

| 结论 | 说明 |
|---|---|
| **生态成熟度** | **极不成熟**。宠物 AI 方向绝大多数是 0–40 star 的个人项目 / 课程作业 / Hackathon，没有一个「事实标准」级别的项目。头部 star 集中在**非 AI 的宠物医院管理系统**（如 `ardalis/ddd-vet-sample` 313★、`pjborowiecki/ARKA…` 165★）。 |
| **最接近「小光景」的项目** | `pavlapintaric235/pet-first-aid-assistant`（急症 RAG + 明确「不给剂量/不催吐/不诊断」安全边界）与 `vancer17/veterinary_agent`（中文、多 Agent、硬安全规则、急症红旗拦截）。两者都**只有 0–1 star、无 LICENSE**。 |
| **唯一可直接商用复用的毒物知识库** | **`Bio-Vet/pet-food-safety`**：数据 **CC BY 4.0**（可商用，需署名）、代码 MIT，101 条、5 物种判定、含毒物剂量与来源引用、俄英双语、兽医审核。**这是本次调研最有价值的可复用资产。** |
| **最大的坑** | 另一个看起来很美的植物毒性数据集 `Luminoid/plantfolio-common-plants` 是 **CC BY-NC-SA 4.0（禁止商用）**，不能用于「小光景」这类商业产品。 |
| **最大空白** | ① 中文「猫+狗同养家庭」多物种家长视角没有任何开源项目；② 宠物行为**科普问答**（而非行为识别模型）几乎空白；③ 无任何开源微信小程序形态的宠物健康 AI。 |

## 9. 总结

### 9.1 宠物方向开源生态的成熟度

**整体：非常不成熟，处于「个人作品集期」而非「生态期」。**

1. **星数断层极其明显**。宠物 AI 相关仓库的 star 中位数是 **0–2**；能过 30 star 的几乎都不是 AI 项目（`ddd-vet-sample` 313★ 是 .NET 教学样例，`ARKA` 165★ 是预约系统）。本方向 star 最高的 AI 项目 `OpenVet-Projects/VetClaw` 也只有 40★。
2. **生命周期极短**。绝大多数项目是课程作业 / Hackathon / 毕业设计，**提交一次即停**。本次调研中 2026 年新出现的项目里，`PawDoctor`、`VetSentinel`、`sules-xialuo/yolov8-cat-behavior-recognition`、`chongchonghaoman/feline-health-advisory` 全部是**创建当日或 2 天内最后一次 push**。
3. **许可状况混乱**。这是最实际的障碍：**最贴合需求的几个项目（`pet-first-aid-assistant`、`veterinary_agent`、`VetVerse`、`feline-health-advisory`、`cat-toxic-plants`）全部无 LICENSE**，法律上不可直接复用。有干净 MIT 许可的（`aicat`、`PawDoctor`、`VetClaw`、`openvpm` 是 AGPL）反而功能或定位有偏差。
4. **工程完备度普遍低于产品线**。有 RAG 的没档案，有档案的没 AI，有 AI 的没安全护栏，有安全护栏的没行为科普——**没有任何一个项目把「档案 + 科普 + 急症引导 + RAG + 高危拦截」这五件事同时做齐**。
5. **商业公司已进场但不开源**。Tomofun（Furbo）办过狗音辨识竞赛（`Splend1d/Tomofun-Challenge`），说明设备厂商在行为识别方向有真实投入，但产出不回流开源。
6. **中国市场空白最大**。中文项目要么是领养/寄养系统（`small-bears` 系，无 AI），要么是毕业设计营销包（无法核实），**没有一个中文、微信小程序形态、面向宠物家长的健康行为 AI 助手**。

### 9.3 空白点（「小光景」的机会）

| # | 空白点 | 「小光景」的对应优势 |
|---|---|---|
| 1 | **「同时养猫和狗」的多物种家庭视角完全空白**。所有项目要么只做猫（`feline-health-advisory`、`cat-alan`、`cat-toxic-plants`），要么只做狗（`Bosc01/stay`、大量犬情绪识别），要么泛化到「宠物」但不区分物种差异 | 「小光景」的猫狗同养家庭定位 + Bio-Vet 的**分物种判定数据**（permethrin：狗 safe / 猫 danger）天然咬合，这是可讲清楚的差异化 |
| 2 | **行为科普问答层缺失**。行为识别项目（YOLO/音频分类）能输出「猫在生气」，但**没有任何项目解释「为什么 / 该怎么办 / 什么情况要就医」** | 「小光景」只做行为科普不做诊断，正好补这一层；可借鉴 `feline-health-advisory` 的「先排危险 → 标准线 → 个体差异 → 行动方案 → 升级阈值」五步框架 |
| 3 | **中文 + 微信小程序形态零供给**。中文项目要么是领养/寄养，要么是毕业设计营销包 | 「小光景」的载体本身就是壁垒；无需与既有开源正面竞争 |
| 4 | **「不做诊断、不开处方、只引导就医」的产品化边界，只有两个小项目做到**（`pet-first-aid-assistant` 1★、`veterinary_agent` 0★）。其余项目都在往诊断/剂量方向走（`PawDoctor`、`VetSentinel`、`VetClaw`、`PawSome-AI` 的处方分析） | 「小光景」的克制定位在合规上是优势，但也意味着**没有现成的行业共识话术可抄**，需要自建。`pet-first-aid-assistant` 的 Safety Scope 清单与 `veterinary_agent` 的硬安全规则是最接近的参考文献（都无许可，只能学思路不能抄代码） |
| 5 | **宠物档案字段没有事实标准**。各项目字段散乱，**「绝育情况」这个「小光景」已有字段在本次调研的所有开源项目文档中都没有被明确列为标准字段** | 「小光景」的档案字段设计（物种/年龄/品种/绝育）需要自己定义，无参照也无冲突 |
| 6 | **开源宠物门店 AI 为零**。门店系统全是学生作业，无 AI | 「小光景」若打通门店（疫苗提醒、驱虫周期、体检预约）是纯增量 |
| 7 | **医院侧对接有现成抓手但许可有坑**。`openvpm` 是唯一现代化、有 REST API + 内置 AI Agent 的开源 PIMS，是「小光景」把急症识别结果转交医院的理想对接面，**但 AGPL-3.0 对闭源商业产品有约束** | 建议：只做 API 层的**数据对接**（不修改其代码、不衍生其作品）以规避传染；或评估 `ARKA`（MIT）的预约能力做替代 |
| 8 | **RAG 出处分级 / 弃答(abstention) 机制几乎没人做**。只有 `Funluned/vetresearch-workbench`（MIT，2★）有 citation verification + abstention，「小光景」的 RAG 知识库若要做可信度，这块是差异化 | 可参考其「引用验证 + 证据不足就弃答」设计，避免幻觉 |

## 附：本次调研的检索与验证方法（可复现）

1. **发现阶段**：GitHub REST Search API `GET /search/repositories?q=<keyword>&sort=stars&order=desc`，约 40 组关键词，覆盖 `pet health assistant` / `veterinary LLM` / `pet triage` / `pet vaccination tracker` / `toxic plants dogs cats` / `aspca toxic` / `dog bark classification` / `cat behavior recognition` / `pet store management` / `宠物 小程序` / `vet clinic management` / `animal behavior dataset` 等中英文组合。
2. **元数据核验**：对每个候选仓库用 `q=repo:owner/name`（可多仓库 OR 合并）拉取 `stargazers_count`、`forks_count`、`license.spdx_id`、`language`、`created_at`、`pushed_at`、`updated_at`、`topics`、`description`。
3. **内容核验**：对高价值项目实际抓取 `https://raw.githubusercontent.com/<owner>/<repo>/HEAD/README.md`、`LICENSE`、`data/items.json`，核对功能清单、技术栈、安全边界、数据字段与许可原文。
4. **本次未使用任何搜索摘要或模型记忆作为数据来源**；所有 star / 许可 / 时间字段均来自上述 HTTP 200 响应的原始 JSON。
